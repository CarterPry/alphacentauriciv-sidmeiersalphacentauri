# BO1 reference: execution architecture and performance lessons

The supplied repository declares a **native Windows engine build**. Its inspected launch path compiles C++ into a 32-bit executable and submits graphics to Direct3D 9. Our current Alpha Centauri player runs the original Windows executable through Wine and Boxedwine's x86-to-WebAssembly execution layer. These are materially different execution paths; visual complexity alone does not establish which has more overhead. This is a source-based architectural comparison, not an FPS benchmark.

| Target/build | C++20, `WIN32`, `/machine:x86`, `WIN32_EXECUTABLE`; release `/O2`; `add_executable` directly includes engine source. `Play.bat` starts `build\\Release\\BO1Zombies.exe`. | The declared target is native Windows. | Graphics | Device creation requests hardware vertex processing; normal mode creates a Direct3D 9 device. Draw code calls `DrawIndexedPrimitive`; buffer creation uses Direct3D vertex/index buffers; presentation calls the swap chain. | Geometry is submitted to the graphics API/GPU. This differs from paying guest instruction costs for old CPU-side image work. |
| CPU organization | `Sys_SpawnRenderThread` creates Win32 events and a `CreateThread` backend. Rendering can hand work to that backend, with a synchronous fallback. Worker jobs use a queue, fences, and an assist-while-waiting path. | The design supports overlapping independent work. The amount of overlap and its benefit depend on settings and workload. |
| Frame loop | `WinMain` repeatedly calls `Com_Frame`; it sleeps when minimized/dedicated. Frame code reads `com_maxfps`, processes events, and invokes server/client stages. | This is a native frame loop. Its source does not provide measured frame times or establish a particular FPS. |
| Measurement | Frame-stage markers and `Present` timing are present; debug CMake configuration enables Tracy. | Separate CPU stages, render waiting, and presentation before choosing an optimization. Instrumentation alone is not a performance result. |

Our selected runtime already uses a repaired JIT with interpreted fallback, rather than exclusively interpreting every instruction. It still executes the original guest program and Wine through the browser runtime. Its accepted actions and remaining limits are recorded in [the runtime report](../runtime/BROWSER_RUNTIME.md); the cost/coverage of interpreted fallback has not yet been measured. The BO1 source cannot quantify that cost.

The Alpha Centauri evidence identifies a useful candidate for measurement: `0x455610` repeatedly applies palette remapping to interface atlases, and `0x5de580` scans the active image clip each time. The conditional full-image total is about 58.6 million pixel inspections during this setup function. This is an inferred workload from code and image dimensions, not a measured bottleneck. [REA startup evidence](../port/startup-findings.md) preserves its conditions and evidence IDs.

The useful lessons are to profile guest execution, image preparation, filesystem calls, and presentation separately; preserve a reproducible workload; then optimize the dominant stage. For a future direct browser implementation, verified engine routines compiled to WebAssembly, cached asset preparation, GPU palette lookup, and queued independent work are reasonable candidates. They require implementation and equivalence testing; the BO1 Windows renderer is not a ready-made browser backend. Making a shader faster would not remove the current guest CPU work unless that work is deliberately moved or eliminated.

No cross-project speed ratio, successful BO1 compilation, smoothness guarantee, or complete absence of third-party compatibility layers is claimed. The actual environment behind the user's smooth-performance observation is unknown. The architecture supports the inference that a richer native 3D game can run smoothly while a simpler game remains slow through guest translation; a comparable-host measurement is required to quantify the difference.
